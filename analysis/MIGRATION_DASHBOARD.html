📋 Migration Rules v3.0

🏗️ Architecture

Standalone Components, Signals, OnPush, ZONELESS

🔒 Security

No innerHTML, no eval, parameterized queries

📝 Naming

kebab-case files, PascalCase classes, camelCase methods

🚫 Prohibited

Zone.js, NgModules, any type, nested callbacks

✅ Required

80% coverage, 0 lint errors, E2E all flows

📊 Quality

SonarQube A rating, <3% duplication

⚠️ Vulnerabilities & Improvements

🔴 CRITICAL: No Rollback Mechanism

If migration fails mid-process, there's no automatic way to revert changes.

✅ Solution: Add Git commit checkpoints after each phase. Create rollback-migration workflow.

🔴 CRITICAL: No Validation Between Phases

Backend might generate invalid schema that breaks frontend generation.

✅ Solution: Add inter-phase validation gates. Run smoke tests before proceeding.

🟠 HIGH: Limited Error Pattern Recognition

test_failure_analyzer.py only recognizes ~10 error patterns.

✅ Solution: Add ML-based pattern matching or expand to 50+ patterns. Add custom pattern config.

🟠 HIGH: No Incremental Migration

Currently all-or-nothing approach. Can't migrate one module at a time.

✅ Solution: Add --modules flag to orchestrate-migration for selective migration.

🟡 MEDIUM: No Progress Persistence

If process crashes, must restart from beginning.

✅ Solution: Add state.json checkpoint file. Resume from last completed phase.

🟡 MEDIUM: No Parallel Processing

Scripts run sequentially, not utilizing multi-core CPUs.

✅ Solution: Use Python multiprocessing in scanners. Parallel component generation.

🟡 MEDIUM: Missing Data Validation Agent

No agent validates migrated data matches original Access DB.

✅ Solution: Add data-validator agent with row count, checksum comparison.

⚪ LOW: No Dry-Run Mode

Can't preview what migration will do without executing it.

✅ Solution: Add --dry-run flag that outputs plan without making changes.
